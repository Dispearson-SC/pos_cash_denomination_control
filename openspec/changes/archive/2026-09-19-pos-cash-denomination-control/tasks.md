**EXTRA (orchestrator decision, not from design.md/tasks.md verbatim)**: `static/tests/tours/offline_queue_tour.js` + `test_offline_queue_is_memory_only` confirms design.md's Discovery table claim ("Offline queue" row) that `PosData`'s offline replay queue (`network.unsyncData`) is memory-only with no persistence layer: a cash-out confirmed while offline is queued, then lost across a page reload while still offline, and no statement line is ever created for it. **CONFIRMED empirically** (previously a static-analysis claim only).

**Deviations from design.md/tasks.md (Phase 13 batch)**:
1. `cash_move_popup_patch.xml`'s reason `<select>`'s `t-on-change` used an inline arrow expression calling `parseInt(...)` directly; this threw `TypeError: ... is not a function` against a real DOM `change` event in the production JS bundle (the Hoot unit tests never exercised this path — they set `popup.state.reasonId` directly instead of dispatching a real event). Fixed by moving the logic into a bound `onReasonChange(ev)` method (`cash_move_popup_patch.js`/`.xml`).
2. `pos_store_patch.js`'s `setup()` initialized `this.vaultAlert` (and the two refresh-tracking fields) *after* `await super.setup(...)`, but `super.setup()` itself calls `this.afterProcessServerData()`, which our own override calls `refreshVaultState()` from — with a *positive* `vault_withdrawal_threshold` already configured at POS load (the vault-alert tour's setup, unlike every Hoot test's usual `0` no-op default), this reached `_pcdcFetchVaultState()` and read `this.vaultAlert.known` before it existed, throwing and aborting the whole POS boot. Fixed by moving the initialization before `await super.setup(...)`.
3. `denomination_breakdown_popup.xml` gained a `data-bill-name` attribute per row (test-targeting only, no behavior change): `pos.bill._load_pos_data_domain`'s `OR pos_config_ids = False` clause means the core seed bills (and any bill created with no `pos_config_ids`) are always allowed for every config regardless of `default_bill_ids`, so a tour cannot assume the popup renders only one row for a "restricted" config; addressing a specific bill by name is currency-format-agnostic and ordering-agnostic.
4. **Empirically confirmed**: `pos.bill.pos_config_ids` and `pos.config.default_bill_ids` are the *same* many2many relation (neither field declares an explicit `relation`/`column1`/`column2`, and there is only one many2many between the two models, so the ORM reuses one junction table for both). `rejection_tour.js`'s "stale allowed-bill" simulation therefore creates a throwaway second `pos.config` and re-points the bill's `pos_config_ids` to it, rather than writing `default_bill_ids` directly (documented in the tour's own comment).
5. `test_rejection_tour` passes `error_checker=lambda message: "RPC_ERROR" not in message` to `start_pos_tour`, and `rejection_tour.js` itself temporarily filters the same string out of `console.error` around the deliberately-triggered rejection (the same technique `generic_helpers/offline_util.js` already uses for `ConnectionLostError` noise): `browser_js` fails a test on *any* browser `console.error` regardless of `error_checker` (`error_checker` only controls early-abort timing, not the final `had_failure` verdict), so the expected, deliberately-triggered `RPC_ERROR` had to be filtered at the source.
6. Every tour except the dedicated opening tour logs in as `pos_admin` rather than the default `pos_user`: the "Cash In/Out" menu option and the one-click vault cash-out both require `_has_cash_move_permission()` (`group_pos_manager` or `account.group_account_invoice`), which the plain `pos_user` fixture lacks. The closing tour still uses `pos_user` (the default), since `closing-manager-override`'s "non-manager" scenario specifically requires a non-manager acting user and does not touch cash-move permission.
